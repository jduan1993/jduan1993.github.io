---
title: 重复查询参数导致接口返回结果异常
---

## 问题描述

当接口请求 URL 中存在重复的同名查询参数时，即使重复参数的值相同或为空，也可能导致接口最终返回结果与单个参数请求不一致。

### 正常情况

请求参数中只存在一个目标参数：

```text
?param=&page=1&size=10
```

接口可以正常返回数据。

### 异常情况

请求参数中存在重复的同名参数：

```text
?param=&page=1&size=10&param=
```

接口返回结果为空或与预期不一致。

---

## 问题原因

HTTP Query Parameter 允许同一个参数出现多次，但不同后端框架或参数绑定方式可能会将重复参数解析为不同的数据结构。

例如：

```text
param=
```

可能被解析为空值或空集合；

而：

```text
param=&param=
```

可能被解析为：

```text
["", ""]
```

如果后续业务逻辑将该参数作为查询条件使用，就可能把空字符串等无效值作为实际筛选条件，从而导致查询结果异常。

例如类似：

```sql
WHERE field IN ('', '')
```

最终可能无法匹配正常数据。

---

## 影响

重复参数可能导致：

* 接口返回空列表；
* 查询结果与预期不一致；
* 相同业务条件下，不同 URL 得到不同结果；
* 前端参数重复拼接时出现隐蔽的数据查询问题。

---

## 建议解决方案

### 1. 前端避免重复参数

构建请求 URL 时，应确保同一个业务参数不会被重复添加。

例如避免：

```text
?param=...&param=...
```

---

### 2. 后端增加参数校验

对于集合类型查询参数，应对以下情况进行统一处理：

* `null`
* 空集合
* 空字符串
* 只包含空字符串的集合
* 重复值

确保无效参数不会被直接作为查询条件使用。

---

### 3. 查询条件动态处理

对于可选查询参数：

* 参数有有效值 → 添加对应筛选条件；
* 参数为空或没有有效值 → 不添加该筛选条件。

避免因为空参数生成无意义的查询条件。

---

## 排查建议

建议在接口参数进入业务逻辑后打印实际解析结果，例如：

```java
log.info("query param = {}", param);
```

重点确认：

```text
单个参数：
param=

重复参数：
param=&param=
```

在后端分别被解析成什么结果，并进一步确认最终生成的查询条件。

---

## 结论

**重复的 Query Parameter 可能因后端参数绑定和查询条件处理方式产生不同的实际语义。**

因此，对于可选查询参数，应避免前端重复传递，并在后端对空值、空集合及无效值进行统一处理，确保相同业务条件下接口行为保持一致。
