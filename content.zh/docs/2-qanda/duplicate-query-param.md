---
title: 重复 Query Parameter 导致接口返回结果异常
---

## 问题描述

当 HTTP 请求 URL 中存在重复的同名查询参数时，即使重复参数的值相同或均为空，也可能导致接口返回结果与仅传递一次参数时不一致。

例如，以下两种请求的查询参数存在差异：

单个参数：

```text
?param=&page=1&size=10
```

重复参数：

```text
?param=&page=1&size=10&param=
```

两种请求虽然包含相同的参数名称和相同的参数值，但接口可能返回不同的结果，例如返回空列表、查询结果不符合预期，或者产生其他不一致的行为。

该问题通常与 HTTP 查询参数的解析方式、后端参数绑定机制，以及后续查询条件的构建逻辑有关。

## 问题原因及分析

### 1. HTTP Query Parameter 允许同名参数重复出现

HTTP URL 的查询字符串可以包含多个同名参数，例如：

```text
?param=value1&param=value2
```

对于重复参数，不同的后端框架、参数绑定方式或自定义解析逻辑，可能采用不同的处理策略，例如：

* **取第一个值**：仅保留首次出现的参数值。
* **取最后一个值**：使用最后出现的参数值覆盖之前的值。
* **保留全部值**：将所有参数值解析为集合或数组。
* **根据参数类型进行绑定**：根据接收参数的类型，将重复参数绑定为单个值或多个值。

因此，不能假定重复参数一定会被忽略，也不能假定不同请求框架对重复参数的处理行为完全一致。

### 2. 空字符串与空集合具有不同的语义

以下参数在文本形式上看起来相似，但解析结果可能存在明显差异：

```text
?param=
```

```text
?param=&param=
```

根据具体的解析和绑定方式，它们可能分别对应：

```java
""
```

以及：

```java
List.of("", "")
```

也可能被解析为其他形式，具体取决于使用的框架及其参数绑定规则。

需要注意以下几种状态并不等价：

* 参数不存在，即 `null` 或未绑定。
* 参数存在，但值为空字符串。
* 参数存在，但解析结果为空集合。
* 参数解析为集合，但集合中的元素均为空字符串。
* 参数包含多个有效值或重复值。

如果后续代码没有明确区分这些状态，就可能在参数校验、条件构建或数据查询过程中产生非预期行为。

### 3. 无效参数可能影响查询条件的构建

如果业务代码直接使用解析后的参数构建查询条件，而没有过滤空字符串等无效值，就可能生成与预期不符的查询表达式。

例如：

```sql
WHERE field IN ('', '')
```

该条件会尝试匹配字段值为空字符串的记录，而不是自动忽略该条件。

如果实际数据不包含符合条件的记录，查询结果就可能为空。

此外，如果不同参数解析结果触发了不同的条件构建分支，也可能导致原本预期相同的请求生成不同的查询条件。

因此，问题的关键不在于重复参数本身必然导致异常，而在于**重复参数经过解析、绑定和后续处理后，可能改变参数的实际语义，进而影响最终的查询逻辑**。

## 最佳实践及分析

### 1. 统一参数解析与校验规则

在接口入口处明确参数的接收类型和处理规则，避免依赖框架未明确约定的默认行为。

对于集合类型参数，应根据接口定义统一处理以下情况：

* 参数缺失。
* 参数值为 `null`。
* 参数值为空字符串。
* 参数解析结果为空集合。
* 集合中包含空字符串或其他无效值。
* 集合中包含重复元素。

需要根据参数的实际语义决定如何处理这些情况，而不是简单地将所有空值和重复值一律删除。

例如，如果参数允许多个有效值，可以先过滤不符合约定的元素，再根据接口定义决定是否去重。

### 2. 区分参数缺失与显式传递空值

参数缺失与显式传递空字符串可能具有不同的语义，应在接口设计阶段明确区分。

例如：

```text
# 参数缺失
?page=1&size=10
```

```text
# 参数存在，但值为空
?param=&page=1&size=10
```

如果某个参数属于可选筛选条件，可以约定：

* 参数缺失：不添加对应的筛选条件。
* 参数为空：根据接口契约决定是忽略该参数，还是执行特定处理。
* 参数包含有效值：按照约定构建筛选条件。
* 参数包含无效值：按照统一的校验规则过滤或拒绝请求。

明确这些规则可以减少参数解析差异对查询结果的影响。

### 3. 动态构建查询条件

对于可选查询参数，应在校验和标准化之后，再决定是否生成对应的查询条件。

推荐遵循以下原则：

* 存在有效参数值时，才添加对应的筛选条件。
* 不存在有效参数值时，根据接口约定决定是否忽略该筛选条件。
* 不应直接将未经校验的空字符串或无效集合传入查询构建逻辑。
* 如果参数不符合接口约定，应根据接口规范选择过滤、返回参数错误或采用其他明确的处理方式。

这样可以避免参数解析结果的细微差异直接改变最终的查询行为。

### 4. 前端避免重复拼接参数

前端构建 URL 时，应避免对同一个业务参数进行无意的重复添加。

尤其是在多个模块共同维护查询参数、复用 URL 参数或进行请求重试时，应检查参数是否已经存在，避免重复追加同名参数。

对于需要传递多个值的参数，应明确采用数组参数、重复键或其他约定格式，并确保前后端对该格式具有一致的理解。

### 5. 加强日志记录与边界测试

排查此类问题时，应重点检查参数从请求进入后端到最终生成查询条件的整个过程。

例如：

```java
log.info("query param = {}", param);
```

对于集合类型参数，还可以记录集合长度、参数标准化后的结果，以及最终生成的查询条件。

同时，建议针对以下情况建立测试用例：

| 测试场景    | 示例                 | 检查重点      |
| ------- | ------------------ | --------- |
| 参数缺失    | `?page=1&size=10`  | 参数是否按预期处理 |
| 单个空参数   | `?param=`          | 空字符串的解析结果 |
| 重复空参数   | `?param=&param=`   | 是否绑定为多个值  |
| 重复相同参数  | `?param=a&param=a` | 重复值的处理规则  |
| 重复不同参数  | `?param=a&param=b` | 多值参数的绑定规则 |
| 混合有效与空值 | `?param=a&param=`  | 无效值的过滤策略  |

通过对比不同输入形式下的参数解析结果和最终查询条件，可以更准确地定位异常发生的阶段。

## 总结

HTTP Query Parameter 允许同名参数重复出现，但不同的解析方式、参数绑定规则和查询条件构建逻辑，可能导致重复参数与单个参数产生不同的实际语义。

排查此类问题时，应重点关注三个环节：**参数解析、参数校验与标准化、查询条件构建**。

在接口设计和开发过程中，应明确重复参数的处理规则，区分参数缺失、空字符串与空集合等不同状态，对无效参数进行统一处理，并避免直接使用未经校验的参数构建查询条件。

同时，应在前端避免无意的重复参数拼接，并通过覆盖边界情况的测试，确保不同请求形式在符合相同参数语义时具有一致的处理结果。
